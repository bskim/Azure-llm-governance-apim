# Azure 기반 Coding Agent LLM Governance Gateway

코딩 에이전트가 사용하는 LLM 백 엔드에 거버넌스를 적용하는 Azure 참조 구현입니다. 코딩 도구와 Microsoft Foundry 모델 사이에 Azure API Management를 두고 Microsoft Entra ID로 호출자를 식별하며, 모델 접근과 토큰 사용량을 한곳에서 관리합니다.

## 왜 필요한가

경쟁력 있는 공개 가중치 모델이 늘면서 Azure에서 선택할 수 있는 모델도 다양해졌습니다. 코딩 에이전트 사용량도 함께 증가해 LLM 요청의 횟수와 크기가 커지고 세션은 길어졌습니다. 이제 한 개발 조직이 여러 코딩 에이전트와 모델을 함께 운영하고, 각 도구가 엔드포인트와 인증 설정을 따로 보유하는 경우가 많습니다.

운영팀은 누가 어떤 모델을 사용했는지, 팀별로 토큰을 얼마나 소비했는지, 요청이 승인된 경로를 통과했는지, 한도에 도달하면 어떻게 처리할지를 알아야 합니다. 각 도구와 공급자에 접근을 따로 설정하면 공통 정책과 사용량 현황을 한곳에서 관리할 수 없습니다.

코딩 에이전트 요청은 이 게이트웨이의 APIM을 거칩니다. APIM은 호출자를 인증하고 적용할 모델과 제한을 확인한 뒤 관리형 ID로 Foundry를 호출합니다. 프롬프트와 응답 본문을 저장하지 않고 사용량을 기록하며, 관리 콘솔에서 정책을 변경하고 적용 결과를 확인합니다.

이 프로젝트에서 토큰 경제성은 호출자, 팀, 애플리케이션, 모델별 토큰 사용량을 측정하고 통제하는 운영 문제를 뜻합니다. 실제 비용은 Azure 청구 내역을 기준으로 판단합니다.

## 대상

Azure에서 소프트웨어 개발과 코딩 에이전트용 LLM 백 엔드를 운영하는 다음 팀을 대상으로 합니다.

- 개발 플랫폼 및 개발자 경험 팀
- Foundry 모델 배포를 관리하는 AI 플랫폼 팀
- 접근 권한, 할당량, 사용량을 담당하는 코딩 에이전트 운영팀
- 분산된 공급자 자격 증명 대신 Entra 인증 경로가 필요한 보안 및 클라우드 플랫폼 팀

## 거버넌스 범위

- Microsoft Entra ID를 이용한 호출자 식별
- 조직, 팀, 개별 주체, 애플리케이션별 모델 접근
- 요청 속도, 토큰 속도, 기간별 할당량, 토큰 예산
- 설정한 임계값에 도달했을 때 승인된 모델로 대체
- 프롬프트와 응답 본문을 기본적으로 저장하지 않는 가명화된 사용량, 정책 결과, 설정 리비전

## 아키텍처

```text
coding agent 또는 호환 client
	|
	| Microsoft Entra access token
	v
Azure API Management /v1
	|
	| managed identity
	v
Microsoft Foundry account /openai/v1
	|
	v
model deployment
```

APIM 경로가 거버넌스 대상 데이터 평면입니다. Foundry 계정이나 프로젝트 엔드포인트로 직접 보낸 트래픽은 이 게이트웨이를 우회하므로 사용량과 정책 결과에 포함되지 않습니다.

## 왜 `/v1`인가

`/v1`은 코딩 에이전트가 사용하는 OpenAI 호환 데이터 평면 API 규약을 나타냅니다. 이 저장소의 버전이 아니며 APIM Basic v2 서비스 계층과도 관계가 없습니다.

게이트웨이는 `/v1/responses`와 `/v1/chat/completions`를 받고 Microsoft Foundry 계정의 `/openai/v1` 엔드포인트를 호출합니다. [Foundry Models v1 API](https://learn.microsoft.com/azure/ai-foundry/openai/api-version-lifecycle)는 OpenAI 클라이언트를 사용할 수 있고 날짜가 붙은 `api-version`을 주기적으로 바꾸지 않아도 됩니다. Responses는 이를 지원하는 Foundry 모델에서 사용할 수 있으며, Chat Completions는 해당 API 규약을 구현한 모델에 적용됩니다.

이 게이트웨이가 구현한 현재 업스트림 경로는 해당 작업을 `/openai/v1` 아래에 정의하며 `/openai/v2` 변형은 정의하지 않습니다. 이후 `/v2`를 지원하려면 업스트림 계약이 먼저 공개되어야 하며 별도의 스키마, APIM 정책, 호환성 테스트, 마이그레이션 안내가 필요합니다.

## 평가 시작

조직에 테스트할 수 있는 Foundry 모델 배포가 있다면 기존 Foundry와 새 APIM을 조합합니다. 거버넌스 데이터 평면을 확인하는 가장 짧은 경로입니다. 적합한 Foundry 모델 배포가 없다면 격리된 리소스 그룹에 모든 항목 생성 모드로 배포합니다.

제어 영역 전용 모드에서는 콘솔과 정책 모델을 평가할 수 있지만 추론 거버넌스를 증명하지는 않습니다.

[PoC 빠른 시작](docs/00-quickstart_ko.md)은 설치, 배포 미리 보기, 최소 거버넌스, 허용 요청, 거부 요청, 콘솔 확인, 제거까지 안내합니다. 모든 모드와 문제 해결 절차는 [상세 배포 가이드](docs/01-deployment_ko.md)에서 설명합니다.

원시 요청으로 게이트웨이 동작을 확인한 뒤 [코딩 에이전트 연결](docs/04-connection_ko.md)을 진행합니다. 직접 연결, 리포지토리 인증 브리지, 선택적 OpenCodex 프로토콜 변환 경로를 설명합니다.

## 사전 요구 사항 요약

권장 평가 경로에는 Node.js 24 이상, PowerShell 7, Azure CLI, Azure Developer CLI가 필요합니다. Docker는 빠른 로컬 테스트에는 선택 사항이고 영속성 통합 테스트에는 필요합니다. 또한 Azure 구독, 리소스와 역할 할당을 생성할 권한, Microsoft Entra 애플리케이션과 서비스 주체를 생성할 권한이 필요합니다.

기존 Microsoft Foundry 계정/프로젝트와 모델 배포를 사용하거나 격리된 모든 항목 생성 모드를 선택할 수 있습니다. 배포는 추론에 Foundry **계정**의 OpenAI 호환 엔드포인트를 사용하며, 프로젝트는 배포 컨텍스트로 기록될 뿐 APIM 백 엔드 URL로 사용되지 않습니다.

종속성을 설치하기 전에 조직이 승인한 패키지 레지스트리를 명시적으로 구성합니다. 패키지 무결성은 고객의 레지스트리 및 패키지 관리자 정책을 충족해야 하며, 누락되거나 일치하지 않으면 거부됩니다. 레지스트리 거버넌스, 라이선스 검토, SBOM, 서명, 릴리스 승인은 고객 조직이 담당합니다.

## 비용 및 보안 고려 사항

이 저장소는 고정 가격 서비스가 아니라 개념 증명입니다. Basic v2 API Management 인스턴스, Microsoft Foundry 모델 사용량, Flex Consumption 실행, 서버리스 Cosmos DB 저장소, Storage와 Key Vault, 프라이빗 엔드포인트, Log Analytics 수집에 각각 비용이 발생할 수 있습니다. 정확한 비용은 지역, 모델, 용량, 트래픽, 보존 기간, 모델 계정 수에 따라 달라집니다. 토큰 수와 할당량은 사용량 통제에 도움을 주지만 실제 비용의 기준은 공급자 청구 내역입니다. [Azure 가격 계산기](https://azure.microsoft.com/pricing/calculator/)를 사용하며 평가가 끝나면 리소스를 제거합니다.

기본 토폴로지는 APIM 데이터 평면을 공개하고 Microsoft Entra 인증을 요구합니다. 영속 거버넌스 저장소와 주체 키 저장소는 프라이빗 네트워크로 구성되며, 템플릿이 지원하는 생성 모델/데이터 리소스에서는 로컬 키 인증이 비활성화됩니다. Foundry 계정에 직접 접근하면 게이트웨이 정책과 원격 분석을 우회하므로 우회를 막아야 할 거버넌스 적용 호출자의 직접 추론 역할을 제거해야 합니다. Webhook URL은 자격 증명이므로 콘솔에서만 설정하고 별도로 안전하게 보관해야 합니다.

## PoC 범위

이 저장소는 거버넌스 대상 요청 경로와 관리 워크플로를 구현합니다. 운영 환경에 적용하려면 조직별로 다음 항목을 결정해야 합니다.

| 영역 | 이 저장소에서 제공하는 기능 | 운영 환경에서 결정할 사항 |
|---|---|---|
| 감사 | 설정 리비전과 운영 이벤트 | 증거 보존, 변조 방지, 접근 검토, 규정 준수 통제 |
| 비용 | 토큰 수, 할당량, 예산, 대체 | 청구서 대조, 비용 배분, 재무 보고 |
| 안정성 | 단일 지역 평가 토폴로지 | 용량 계획, 부하 테스트, SLO, 고가용성, 재해 복구 |
| 네트워크 | Entra 인증으로 보호하는 공개 Basic v2 APIM 수신 경로 | 비공개 수신 경로, 비공개 Foundry 연결, DNS, 직접 모델 접근 제거 |
| 클라이언트 호환성 | Responses, Chat Completions, 검증한 브리지 및 프록시 계약 | 지원할 클라이언트 버전, 릴리스 테스트, 어댑터 관리 주체 |

예산은 best effort 방식으로 적용되므로 이미 처리 중인 요청은 상한을 넘겨 완료될 수 있습니다. 접근 권한 회수는 발급된 토큰이 만료되거나 갱신될 때 적용됩니다. 이는 측정된 PoC 한계이며 청구 금액의 상한이나 즉각적인 권한 회수를 보장하지 않습니다.

## 평가 사용자 지정

배포 설정에는 `azd env set`을 사용하고, 모델, 팀, 제한, 예산, 대체, 알림은 관리 콘솔에서 관리합니다. 클라이언트가 보내는 논리적 모델 별칭과 Microsoft Foundry에 설정한 공급자 배포 이름을 구분합니다. 30일 유효 기간이 끝나기 전에 모델 카탈로그를 새로 고칩니다.

정책 조합의 의미를 바꾸는 작업은 콘솔 설정이 아니라 코드 수준의 사용자 지정입니다. 배포 가이드는 권한 부여 평가기, 유효 정책 작성기, 대체 컴파일러, 버전 관리 계약, APIM 정책을 함께 변경해야 하는 지점을 설명하며, 관련 테스트와 정책 버전도 함께 갱신해야 합니다.

## 첫 번째 troubleshooting 확인

- `/api/healthz`에서 `200`이 반환되면 제어 평면 호스트에 연결할 수 있다는 뜻이며 추론 준비가 완료됐다는 뜻은 아닙니다.
- 최초 게시 전에 `503 governance_unavailable`이 반환되면 완전한 활성 거버넌스 리비전 또는 공급자 매핑이 없는 상태입니다.
- `403 model_not_allowed`는 인증은 성공했지만 정책이 요청 모델을 거부한 것이므로 재시도하지 않습니다.
- 관리 경로의 본문 없는 `403`은 거버넌스 콘텐츠가 아니라 App Service 인증 설정을 확인해야 한다는 뜻입니다.
- Microsoft Foundry에 직접 보낸 요청은 게이트웨이 사용량이나 정책 결과에 표시되지 않습니다.

## 평가 완료 기준

- [ ] 허용된 요청이 APIM `/v1` 엔드포인트를 거쳐 `200`을 반환합니다.
- [ ] 허용되지 않은 모델이 백 엔드에 도달하지 않고 `403`을 반환합니다.
- [ ] 콘솔에서 활성 설정과 호출자별 모델 접근을 확인합니다.
- [ ] 프롬프트와 응답 본문 없이 토큰 사용량을 확인합니다.
- [ ] 거버넌스를 변경한 뒤 새 리비전이 표시됩니다.
