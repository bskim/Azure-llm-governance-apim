# 평가 환경 운영 및 제거

이 운영 지침은 특정 환경에 종속되지 않는 평가 환경 운영 및 제거 절차를 설명합니다. 안전하게 작업할 수 있는 범위와 승인이 필요한 단계를 정의하며, 이 문서 자체가 환경 접근을 승인하지는 않습니다.

## 이 운영 지침의 범위

평가마다 고객이 선택한 전용 환경과 리소스 범위를 사용합니다. 식별자는 공개 문서가 아닌 고객이 통제하는 운영 시스템에 기록합니다.

이 지침은 다음을 다룹니다.

- 저장소의 로컬 준비
- 별도 승인이 필요한 검증, 배포, 운영, 제거
- 실행 중인 정책 확인
- 소유권을 확인한 뒤 수행하는 제거

## 승인 범위와 작업 단계

저장소의 로컬 검사는 코드와 설정의 일관성만 확인합니다. 클라우드 배포 준비 상태, 접근 권한, 배포 성공, 데이터 평면 동작, 제거 대상의 소유권까지 입증하지는 않습니다.

각 단계는 별도로 승인합니다.

| 단계 | 고객이 결정할 사항 |
|---|---|
| 로컬 준비 | 사용할 소스 리비전과 검사 항목 |
| 검증 | 확인할 대상과 읽기 전용 작업 |
| 리소스 프로비저닝 및 배포 | 생성하거나 갱신할 리소스와 산출물 |
| 운영 | 테스트할 호출자, 엔드포인트, 모델, 텔레메트리 |
| 제거 | 소유 리소스 중 삭제하거나 영구 삭제(purge)할 대상 |

승인은 명시된 작업, 대상, 실행 주체, 시간 범위에만 적용됩니다. 이전 로그인, 보유 역할, 검사 성공을 이후 작업의 승인으로 간주하지 않습니다.

## 평가 경계 정의

리소스를 프로비저닝하기 전에 다음을 기록합니다.

- 선택한 환경 이름과 구독
- 평가 환경이 소유하는 리소스 그룹
- 외부 의존성으로 유지할 재사용 리소스
- 변경하면 안 되는 기존 리소스
- 평가를 위해 별도로 만든 ID와 디렉터리 개체

이름, 접두사, 리소스 그룹 소속, 설정에서의 참조는 소유권을 증명하지 않습니다. 엔드포인트, 배포, ID 또는 그룹을 재사용한다고 해서 삭제할 권한까지 이전되지는 않습니다.

## 저장소의 로컬 준비

조직이 승인한 패키지 레지스트리 정책을 구성한 뒤 저장소에 문서화된 로컬 검사를 실행합니다. 패키지 무결성 정보는 해당 레지스트리와 패키지 관리자 정책을 충족해야 합니다. 정보가 누락되거나 일치하지 않으면 패키지를 거부해야 합니다. 승인된 정책이 없으면 작업을 차단하거나 검증을 미완료 상태로 남깁니다.

레지스트리 관리, 라이선스 및 SBOM 검토, 서명, 릴리스 승인은 고객이 담당합니다. 로컬 검사가 이러한 승인을 대신하지는 않습니다.

테스트한 소스 리비전, 명령, 종료 상태, 건너뛴 검사, 해결되지 않은 실패는 고객이 통제하는 시스템에 기록합니다. 특정 환경의 기록이나 내부 검토 자료는 공개 문서에 게시하지 않습니다.

## 검증 및 배포

클라우드 작업을 실행하기 전에 현재 인증 정보와 대상 범위를 확인합니다. 미리 보기에서 생성, 갱신, 삭제 항목과 외부 의존성, 보호 리소스를 검토합니다.

고객이 정확한 대상과 작업을 승인한 뒤에만 프로비저닝하거나 배포합니다. 배포 미리 보기는 프로비저닝 승인이 아니며, 배포 승인에 데이터 평면 테스트나 제거 승인이 포함되지는 않습니다.

## 평가 운영

### 시작 전 확인

거버넌스가 적용되는 요청을 보내기 전에 다음을 확인합니다.

- 현재 환경과 리소스 범위를 확인합니다.
- 재사용 의존성이 참조 전용으로 표시되어 있는지 확인합니다.
- 관리자 및 게이트웨이 엔드포인트가 이번 배포에서 생성된 값인지 확인합니다.
- 활성 거버넌스 리비전과 공급자 매핑이 완전한지 확인합니다.
- 대상이 보호 리소스이거나 소유하지 않은 리소스로 확인되면 중지합니다.

### 실행 결과 해석

- `/api/healthz`의 `200`은 제어 평면에 연결할 수 있다는 사실만 확인해 줍니다.
- `403 model_not_allowed`는 정책에 따른 거부이므로 일시적 장애처럼 재시도하지 않습니다.
- `503 governance_unavailable`은 필요한 거버넌스 데이터를 모두 사용할 수 없다는 뜻이며, 호출자의 권한에 따른 거부는 아닙니다.
- 사용량 기록에는 프롬프트나 응답 본문 대신 토큰 수가 있어야 합니다.
- 대체 경로(fallback)가 요청한 모델을 변경하면 실제 사용한 모델을 기록합니다.

Foundry에 직접 보내는 요청은 게이트웨이의 정책과 텔레메트리를 우회하므로 게이트웨이 동작을 검증하지 못합니다.

### 중지 조건

다음 경우에는 작업을 중지하고 진행 여부를 다시 승인받습니다.

- 대상이 승인된 범위를 벗어난 경우
- 계획에 보호 리소스나 소유하지 않은 리소스가 포함된 경우
- 소유권 기록이 없거나 서로 모순되는 경우
- 하나의 명령이 별도 승인이 필요한 단계를 함께 실행하는 경우
- 결과가 일부만 확인되거나, 확인 불가능하거나, 예상한 범위와 일치하지 않는 경우

작업을 성공시키려고 대상 범위를 넓히지 않습니다. 정상 동작이 확인된 마지막 활성 거버넌스 리비전을 보존합니다.

## 제거 전 승인 확인

제거에는 환경, 대상, 허용된 단계를 명시한 명시적 승인이 필요합니다. 사전에 받은 유효한 승인이 해당 단계를 이미 포함한다면, 범위가 유지되는 동안 같은 승인을 반복해서 받지 않아도 됩니다. 삭제 또는 영구 삭제 전에 제거 미리 보기를 검토합니다.

제거 미리 보기에 사용하는 정확한 ID 기반 소유권 조회 결과(readback)의 유효 시간은 최대 30분입니다. 별도로 승인된 각 삭제 또는 영구 삭제 단계 전에 조회 결과를 새로 수집하고 무결성 검증용 다이제스트로 다시 봉인합니다. 사전 승인도 이 증빙의 유효 시간을 연장하지는 않습니다. 조회 결과가 유효하지 않거나, 관측 시각이 미래이거나, 30분보다 오래되었거나, 소유권 매니페스트 생성 전이거나, 단계 승인 시점에 만료되었으면 승인이 거부됩니다.

각 제거 후보에 대해 다음을 확인합니다.

- 전체 리소스 ID 또는 디렉터리 개체 ID
- 해당하는 경우 리소스 유형과 소속 리소스 그룹
- 고객이 통제하는 생성 또는 소유권 기록
- 평가 전에 존재했는지 여부
- 삭제가 재사용 중이거나 보호된 의존성에 영향을 줄 수 있는지 여부

소유권이 불분명한 후보는 제외합니다. 평가 환경이 소유하고 삭제 승인을 받았으며 식별자가 여전히 일치하는 리소스만 삭제합니다. 식별자가 달라졌다면 이름이 비슷한 리소스로 대체하지 않습니다.

다음 작업은 구분해서 수행합니다.

- 제거 미리 보기
- 클라우드 리소스 삭제
- 디렉터리 개체 삭제
- 일시 삭제된 API Management 리소스 영구 삭제
- 일시 삭제된 Key Vault 리소스 영구 삭제

삭제 완료만으로는 이름을 재사용할 수 있는지, 디렉터리 개체가 사라졌는지, 일시 삭제된 리소스가 영구 삭제되었는지 알 수 없습니다. 영구 삭제 가능 여부는 서비스의 보존 정책과 운영자 권한에 따라 달라집니다.

### 일시 삭제 및 이름 재사용

- Key Vault의 영구 삭제 보호는 설정된 일시 삭제 보존 기간 동안 유지됩니다. 보호된 자격 증명 모음은 보존 기간이 만료되기 전에 영구 삭제할 수 없습니다.
- API Management의 삭제와 영구 삭제는 필요한 권한이 서로 다른 별도 작업입니다.
- Entra 디렉터리 개체 삭제는 리소스 그룹 삭제와 별개입니다. 서비스 주체는 복구 가능한 삭제 항목으로 남을 수 있으므로, 활성 목록에 없다는 사실만으로 영구 삭제를 입증할 수는 없습니다.

제거 후에는 삭제, 보존, 미확인, 일시 삭제 상태의 대상을 각 작업의 정확한 소유권 증빙과 대조하고 고객이 통제하는 시스템에 기록합니다. 테넌트 전체를 일괄 영구 삭제하지 않습니다. 일부만 완료되었다면 부분 완료로 보고합니다.

## 운영 중 정책 확인

### 모델 접근

조직의 모델 목록은 접근 권한 부여 목록이 아니라 허용 범위의 상한입니다. 적용 가능한 팀, 주체, 애플리케이션의 허용 모델을 합집합으로 결합한 뒤 조직의 상한 안으로 제한합니다.

모든 호출자에게는 적용 가능한 팀, 주체 또는 애플리케이션의 권한 부여가 하나 이상 필요합니다. 조직의 상한 밖에 있는 모델을 개별적으로 허용해도 해당 모델에 접근할 수 없으며, 조직의 상한이 넓어지지도 않습니다.

### 정책 거부와 데이터 부재의 구분

- `403`은 게이트웨이가 호출자에게 적용할 정책을 확인한 뒤 요청을 거부했다는 뜻입니다.
- `503`과 `Retry-After`는 필요한 ID 또는 정책 데이터를 모두 사용할 수 없었다는 뜻입니다.

두 결과는 조사해야 할 원인이 다르므로 구분합니다.

### 한도, 예산 및 대체 경로

- 분당 요청 한도와 토큰 한도는 독립적이며, 각 카운터에는 적용 가능한 값 중 가장 낮은 값이 적용됩니다.
- 할당량은 시간당 사용률로 환산해 비교하되, 선택된 할당량은 설정 당시의 수량과 기간을 유지합니다.
- 적용 가능한 모든 예산은 독립 카운터를 유지하며, 하나라도 소진되면 요청을 차단할 수 있습니다.
- `HARD_BLOCK`은 토큰 한도에서 차단하고, `SOFT_WARNING`은 한도에서 경고한 뒤 추가 허용량까지 소진하면 차단합니다. `THROTTLE`은 자체적인 총량 차단 없이 요청 속도 제한 단계를 적용합니다. 설정 방법과 폴백 없는 차단 예시는 [예산 동작](02-administration_ko.md#예산-동작)에서 설명합니다.
- 이미 처리 중인 요청은 완료될 수 있으므로 예산은 엄격한 지출 상한이 아닌 best effort 방식으로 적용됩니다.
- 대체 경로 계획은 정확히 하나만 적용됩니다. 애플리케이션, 주체, 팀, 조직 순서로 더 구체적인 범위의 계획을 선택합니다.
- 더 구체적인 대체 경로 계획은 상위 범위의 계획과 병합되지 않고 이를 대체합니다.
- 폴백은 요청당 최대 하나의 모델 연결을 사용합니다. 허용된 연결이 없으면 요청 모델에 쿼터와 예산이 그대로 적용됩니다. 참조 구현의 `onExhausted: deny` 설정은 배포된 APIM 제어가 아닙니다. [기존 폴백 계획 편집](02-administration_ko.md#기존-폴백-계획-편집)에서 자세히 설명합니다.

에이전트는 대화와 작업 공간 맥락을 다시 전송하므로, 한도를 설정하기 전에 실제 사용을 대표하는 코딩 에이전트 트래픽을 측정합니다.
