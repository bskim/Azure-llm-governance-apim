# 관리 콘솔 사용하기

콘솔에서는 게이트웨이의 동작을 확인하고 허용 범위를 변경합니다. 이 안내서는 콘솔을 처음 사용하는 관리자가 각 화면의 정보와 의미를 이해하고, 실제 응답과 응답이 없는 상태를 구분할 수 있도록 필요한 순서로 설명합니다.

다음 두 가지 원칙은 콘솔 전체에 적용됩니다.

**bootstrap import는 한 단계로 승인되고 게시되지만, 이후 지원되는 변경은 초안으로 저장됩니다.** 다른 쓰기 권한 관리자가 초안을 재개해 승인하고 게시해야 합니다. 명시적으로 구성된 자체 승인 권한이 있는 경우에만 예외가 적용되며, lifecycle에는 해당 승인이 예외로 기록됩니다. 새 리비전은 모든 게시 대상이 확인된 뒤에만 요청에 적용됩니다. 게시가 중단되면 호출자는 이전 활성 리비전을 계속 받습니다.

**필요한 데이터를 확인할 수 없으면 화면은 빈 결과를 보여주는 대신 거부 사유를 표시합니다.** 빈 테이블은 기록은 있지만 항목이 없는 상태이고, 한 번도 기록된 적이 없는 저장소는 데이터 자체가 없는 상태입니다. 콘솔은 이 두 상태를 구분해 표시합니다. 이유 코드가 붙은 거부는 제품이 알 수 없는 내용을 추측해 표시하지 않는다는 뜻입니다.

이 페이지의 스크린샷은 Azure 배포 결과가 아니라 합성 fixture를 사용하는 현재 로컬 deterministic UI입니다. Demo persona, DEV 선택기, 예시 수치는 로컬 전용 예시입니다. 배포된 콘솔에는 로그인할 때 사용한 계정이 표시됩니다.

## 콘솔 접속하기

콘솔 URL은 배포의 `ADMIN_INTERFACE_ENDPOINT` 출력값입니다. 배포 중에 부여된 관리자 역할이 있는 Microsoft Entra 계정으로 로그인합니다. 역할을 부여하고 변경하는 방법은 [게이트웨이 배포하기](01-deployment_ko.md)에서 설명합니다.

수행할 수 있는 작업은 화면이 아니라 계정의 역할에 따라 결정됩니다. 읽기만 가능하고 변경할 수 없는 화면에서는 클릭한 뒤 거부되는 버튼을 보여주는 대신, 조작할 수 없는 영역마다 **Read-only**를 표시합니다.

## 개요

![개요 화면](images/console-overview.png)

상태 요약 행에서는 배포가 정상적으로 동작하는지 빠르게 확인할 수 있습니다. 현재 서비스 중인 설정, 사용량 집계 완료 여부, 정합성 확인의 최신 여부, 메시지 본문 보관 여부를 보여줍니다. 본문 보관의 기본값은 `Disabled`이므로, 별도로 결정하지 않았다면 그대로 유지해야 합니다.

아래에는 각 수치의 출처도 함께 표시됩니다. `Reported`와 `Fresh`는 해당 수치가 게이트웨이 자체의 사용량 집계에서 나왔고, 수치가 다루는 기간이 이미 마감되었다는 뜻입니다.

**`Unknown`은 정보 공백이 아니라 하나의 응답입니다.** 배포된 사용량 경로에서 중앙값 지연 시간이나 오류율을 수집하지 않으면 해당 값은 `Not collected`으로 표시됩니다. 스크린샷의 로컬 fixture 값은 Azure 측정값이 아닙니다. 제품이 측정할 수 없는 수치는 임의의 숫자로 채우지 않고 이처럼 표시합니다.

## 게시

![게시 화면](images/console-lifecycle.png)

변경 사항이 호출자에게 반영되었는지 확인하려면 이 화면을 엽니다. 배너에는 현재 서비스 중인 리비전이 표시됩니다. 그 아래에는 작성·승인·게시 과정에 기록된 lifecycle 가명 관리자 코드와 확인된 게시 대상이 표시됩니다. bootstrap 작성에는 bootstrap code만 사용합니다. 이후 배포된 관리자 쓰기에는 인증된 관리자의 검증된 테넌트 및 개체 식별자에서 배포 키로 파생한 안정적인 버전별 가명 관리자 코드를 사용합니다. 이 코드로 활성 키 버전이 유지되는 동안 관리자를 구분할 수 있지만, 식별자, 이름, 이메일, claim 또는 자격 증명은 저장하지 않습니다. 관리자 신원을 확인할 수 없는 쓰기는 저장하거나 게시하기 전에 `caller_not_identifiable`로 거부됩니다.

확인된 게시 대상 수가 전체보다 적은 리비전은 아직 게시 중이라는 뜻입니다. 이 경우 호출자는 계속 이전 리비전을 받습니다.

이후 초안은 작성자가 승인할 수 없습니다. 다른 쓰기 권한 관리자가 재개해 별도 승인을 기록하고 게시해야 합니다. 명시적으로 부여된 자체 승인 권한은 일반 검토가 아니라 자체 승인으로 기록됩니다.

승인 또는 재시도를 위해 콘솔은 승인 전용 요청 `{ "resume": true, "revisionId": "revision-0002" }`을 보냅니다. 이 요청은 이미 저장된 제안만 식별하며 설정이나 변경 필드를 포함하지 않습니다. 서비스는 변경할 수 없는 저장된 제안을 읽어 게시하므로 검토자가 내용을 대체할 수 없고, 기록된 작성자가 계속 게시된 내용의 작성자로 남습니다.

대상 처리에 실패하면 lifecycle이 `failed`로 바뀝니다. 원인을 해결한 뒤 저장된 제안을 재시도하면 아직 완료되지 않은 대상만 다시 시도합니다. 초안을 바꾸려면 작성자가 먼저 철회하고 새 제안을 제출해야 합니다. 초안 작성자는 `POST /v1/admin/governance/publish`와 `{ "command": "withdraw", "revisionId": "revision-0002" }`를 사용해 자신이 아직 승인하지 않은 제안을 포기할 수 있습니다. 이 작업은 내용을 게시하지 않고 종료된 withdrawal을 기록합니다. reader나 다른 관리자는 withdrawal할 수 없습니다.

콘솔은 서비스가 recovery abandonment를 허용할 때만 `{ "command": "abandon", "revisionId": "revision-0002" }`를 표시합니다. 이를 사용하려면 legacy, bootstrap 또는 shared author의 draft, approved, failed 또는 publishing 제안에 verified 대상이 없어야 하고, 작성자를 현재 관리자와 일치시킬 수 없어야 합니다. publish capability와 높은 수준의 own-approval capability도 모두 필요합니다. verified 대상이 하나라도 있으면 `proposal-abandonment-verified-targets`로 거부되며, 게시 작업이 시작된 draft 또는 approved도 거부됩니다. 이 경우에는 복구한 뒤 재시도해야 합니다. 저장된 제안이 없는 legacy revision의 내용도 대체할 수 없습니다. verified 대상이 있으면 `legacy-recovery-required`를, 하나도 없으면 높은 권한 관리자가 abandonment 후 새 제안을 만들 때까지 `legacy-recovery-abandon-required`를 반환합니다.

## 예산

![예산 화면](images/console-budgets.png)

예산은 이 화면에서 작성하며 게시되는 순간부터 적용됩니다. 화면에서는 설정한 값과 실제로 강제되는 값을 구분해 보여줍니다. 두 값은 서로 다른 의미이기 때문입니다.

예산은 best effort 방식으로 동작합니다. 강제 적용이 따라잡기 전에 상한을 넘을 수 있으며, 화면에는 초과한 정도가 표시됩니다. 어떤 요청도 특정 수치를 넘지 않는다는 강한 보장이 필요하다면 이 제품은 그런 보장을 제공하지 않습니다. 자세한 한계는 [게이트웨이 배포하기](01-deployment_ko.md#운영상의-한계)에 정리되어 있습니다.

예산은 하나의 숫자로 합산되지 않으며, 적용 가능한 각 카운터가 요청을 차단할 수 있습니다. 게시와 강제 적용 과정에서 작성된 예산 식별자, 버전, 범위, 모델, 기간, 동작, 기준값, 산정 기준이 유지됩니다. 지원하지 않거나 모호한 조합은 카운터를 조용히 공유하지 않고 게시 전에 거부합니다. 결합 규칙은 [평가 환경 운영 및 제거](03-operations_ko.md)의 정책 확인에서 설명합니다.

### 예산 동작

예산은 금액이 아니라 토큰 기준입니다. 산정 기준은 `apim-estimated-total-tokens`이며, 실제 금액은 Azure 청구 내역으로 확인합니다. 예산 동작과 모델 폴백은 별도 설정입니다.

| 동작 | 처리 방식 | 임계값 설정 |
|---|---|---|
| `HARD_BLOCK` | 설정한 토큰 할당량이 소진되면 차단합니다. 추가 허용량은 없습니다. | 사전 경고가 필요하면 `warnAtBasisPoints`를 1~9,999로 설정합니다. |
| `SOFT_WARNING` | 설정 한도 부근에서 경고하고, 한도와 추가 허용량을 모두 소진하면 차단합니다. 경고만 하고 무제한 허용하는 동작은 아닙니다. | `graceBasisPoints`를 1~10,000으로 설정해야 합니다. |
| `THROTTLE` | 설정한 사용률 임계값에서 요청 속도 제한 단계를 적용합니다. 자체적으로 토큰 총량을 차단하지는 않지만, 함께 적용되는 다른 할당량이 요청을 차단할 수 있습니다. 속도를 초과한 요청에는 `429`를 반환합니다. | 1~20,000 범위의 `atBasisPoints`를 오름차순으로 지정하고, 각 단계에 지원되는 `tierCode`를 선택합니다. |

임계값 단위는 베이시스포인트입니다. 100은 1%, 500은 5%, 10,000은 100%입니다. 예산이 1,000,000토큰이면 `HARD_BLOCK`의 차단 한도는 1,000,000토큰입니다. `SOFT_WARNING`에 `graceBasisPoints: 500`을 설정하면 1,000,000토큰 부근에서 경고하고 1,050,000토큰에서 차단합니다. APIM 경고 임계값은 정수 백분율로 변환되므로 실제 경고 시점은 작성한 임계값과 다를 수 있습니다. 두 경우 모두 best effort 방식으로 적용됩니다.

현재 배포가 지원하는 단계는 `tier-reduced`와 `tier-minimal`입니다. 요청 속도는 게이트웨이에서 배포의 `requestsPerMinute`를 각각 2와 10으로 나눈 뒤 소수점 이하를 버린 값으로 설정하며, 최솟값은 분당 1회입니다. 콘솔에서는 단계와 적용 임계값을 선택하며, 새 단계 코드를 만들거나 요청 속도 자체를 변경하지는 않습니다. 예를 들어 스로틀 예산에 8,000베이시스포인트에서 `tier-reduced`, 9,500에서 `tier-minimal`을 적용하도록 설정할 수 있습니다. 이는 설명을 위한 예시이며 운영 환경의 권장 기본값은 아닙니다.

### 예산 추가 및 편집

1. 쓰기 권한이 있는 관리자가 **예산** 화면에서 예산을 추가하거나 기존 행을 편집합니다. 읽기 권한만으로는 변경할 수 없습니다.
2. 새 예산은 `organization`, `team`, `subject`, `application` 중 적용 범위를 선택합니다. 기존 예산의 범위는 편집할 수 없으며, 범위를 바꾸려면 삭제와 추가를 별도로 검토해야 합니다.
3. 모델 범위는 `all-models` 또는 `per-model`을 선택합니다. 모델별 예산은 게시된 모델 카탈로그에서 논리적 모델 키를 선택해야 하며, 조직과 팀 범위에서만 지원합니다. 주체와 애플리케이션 범위에서는 전체 모델 예산만 지원합니다.
4. 기간은 `Hourly`, `Daily`, `Weekly`, `Monthly`, `Yearly` 중에서 선택하고, 토큰 한도는 양의 정수로 입력합니다.
5. 동작과 해당 임계값을 설정합니다. 편집에서는 한도, 기간, 모델 범위, 동작, 임계값을 변경할 수 있습니다. 전체 모델로 전환하면 개별 모델 키가 제거됩니다. 지원하지 않는 조합이나 중복되는 예산 적용 범위는 거부됩니다. 같은 적용 범위와 모델 범위에는 할당량 예산(`HARD_BLOCK` 또는 `SOFT_WARNING`) 하나와 `THROTTLE` 예산 하나를 함께 설정할 수 있습니다. 기간만 다르게 선택해도 같은 종류의 예산을 추가로 만들 수는 없습니다.
6. 변경을 제안한 뒤 [게시](#게시)의 승인·게시 절차를 진행합니다. 초안을 저장하는 것만으로 활성 예산이 바뀌지는 않습니다. 명시적인 자체 승인 권한이 있는 경우를 제외하면 다른 쓰기 권한 관리자가 승인하며, 게시 대상의 검증이 완료된 뒤에만 변경 사항이 적용됩니다.

예산 설정을 실제로 변경하면 새 버전이 부여되며, 변경 사항이 없는 제출은 거부됩니다. APIM 카운터 키에는 예산 ID와 버전이 포함되므로 새 버전이 이전 버전의 소비 카운터를 이어받지는 않습니다. 따라서 예산 편집으로 같은 청구 기간의 누적값이 연속해서 유지된다고 가정하지 않습니다. 사용량 이력은 별도 기록으로 남습니다.

### 폴백 없이 특정 모델 차단

다른 모델로 전환하지 않고 한 모델의 사용량을 제한하려면 조직 또는 팀 범위의 `per-model` 예산을 사용합니다. 대상 모델, 기간, 토큰 한도를 지정하고 `HARD_BLOCK`을 선택합니다. 적용 가능한 폴백 계획은 비활성화하거나 구성하지 않습니다. 사전 경고 임계값은 선택 사항이며, 이를 설정한다고 폴백이 자동으로 활성화되지는 않습니다.

해당 모델의 할당량이 소진되면 APIM은 Foundry에 전달하기 전에 요청을 거부하고 `403 token_quota_exceeded`와 `Retry-After` 헤더를 반환합니다. 다른 모델을 선택하지 않으며, 기간이 초기화되거나 관리자가 적용 한도를 변경할 때까지 차단됩니다. 이 예산 자체가 다른 모델까지 차단하지는 않지만, 다른 모델에도 각자의 한도와 공통 한도가 적용됩니다. 이미 처리 중인 요청은 완료될 수 있으므로 정확한 금액 기준의 지출 상한을 보장하지는 않습니다.

## 모델

![모델 화면](images/console-models.png)

카탈로그에는 각 모델의 기능, 이 배포가 허용하는 범위, 실제 서비스한 모델, Azure가 공개하는 meter(사용량 계측 단위)가 표시됩니다.

모델을 거버넌스 대상으로 지정할 때는 이 배포의 모델 배포 중 하나를 선택합니다. 콘솔은 이름을 직접 입력받지 않고 배포에서 선택지를 읽어옵니다. 모델을 제거하려면 사유를 입력해야 하며, 이용 권한(호출자에게 부여된 권한)으로 여전히 허용된 모델은 제거할 수 없습니다. 따라서 호출자에게 아직 이용 권한이 있는 모델이 카탈로그에서 조용히 빠지는 일은 없습니다.

이용 권한을 철회해도 모델 참조는 삭제되지 않습니다. 철회된 바인딩이 여전히 참조하는 모델을 제거하려면 참조를 일관되게 정리한 전체 설정 교체안을 승인하고 게시해야 합니다. 콘솔의 개별 편집기는 바인딩을 삭제하지 않습니다. 제공자 캡처 및 가격 조회 컨트롤은 생성된 배포 설정이 해당 경로를 제공한다고 명시할 때만 표시되며, 지원되는 배포 모드는 이 설정을 제공합니다.

카탈로그는 버전과 만료 시각이 있는 특정 시점의 캡처 값입니다. 만료되기 전에 제공자로부터 새로 고쳐야 하며, 그렇지 않으면 화면에 오래된 값이 표시된다는 알림이 나타납니다.

## 폴백

![폴백 화면](images/console-fallback.png)

다운그레이드 계획은 호출자가 요청한 모델을 받을 수 없을 때의 동작을 결정합니다. 특정 호출자에게는 정확히 하나의 계획만 적용됩니다.

이 화면에서는 세 가지를 확인할 수 있습니다. 무엇이 작성되었는지, 호출자가 거칠 수 있는 hop(대체 모델로 넘어가는 각 단계)과 각 hop을 허용하거나 거부한 규칙, 지금 요청이 들어오면 어떤 일이 발생하는지입니다. 계획이 없는 scope는 계획 없음으로 표시합니다. 요청 패널도 아무 일도 일어나지 않는다고 암시하지 않고, 결정을 표시할 수 없다고 알려줍니다.

계획이 요청을 다른 모델로 보내더라도 응답을 그 사실이 드러나지 않게 바꾸지 않습니다. 따라서 호출자는 지정하지 않은 모델의 응답을 받을 수 있으며, 이 화면과 사용량 기록에는 실제 응답 모델이 표시됩니다.

### 기존 폴백 계획 편집

편집기는 기존 계획의 활성화 상태, 모델 선택 의도, 대체 알림 설정을 보존합니다. 계획의 식별자, 대상, 작성 주체, 유효 기간은 바꾸지 않고 모델 연결을 교체할 수 있습니다. 새 범위의 계획을 만들려면 여전히 전체 설정 교체안을 승인하고 게시해야 합니다.

1. 변경할 기존 계획의 범위를 선택합니다. 요청에 대체 모델을 허용하려면 폴백을 활성화하고 선택 의도를 `preferred`로 지정합니다. `pinned`는 요청한 모델을 유지합니다.
2. 등록된 모델 별칭으로 출발 모델과 대상 모델의 연결을 추가·제거·변경합니다. 계획에는 최대 32개 연결을 둘 수 있으며, 자기 자신으로의 연결, 순환, 같은 출발 모델의 여러 대상 연결은 거부됩니다.
3. 요청 하나에는 연결 하나만 적용되며(`maxDepth: 1`), 여러 단계를 연속으로 거치지 않습니다. 여러 연결은 서로 다른 요청 모델의 대체 경로를 나타냅니다.
4. 화면의 호출자·API 계열별 컴파일 결과는 미리 보기이며 모든 호출자의 동작을 보장하지 않습니다. 실제 호출자를 기준으로 모델 등록, 이용 권한, API 계열 호환성을 확인합니다. 미리 보기가 더 낮은 가격, 동등한 기능, 데이터 상주 요건까지 입증하지는 않습니다.
5. 변경한 초안을 제출하고 [게시](#게시) 절차를 완료합니다. 같은 연결의 순서만 바꾸는 것은 정책 변경이 아닙니다. 초안을 저장하는 것만으로 새 연결이 활성화되지는 않습니다.

APIM은 계획이 활성화되고 선택 의도가 `preferred`이며 구성된 사용량 임계값에 도달했을 때 허용된 연결을 사용합니다. 허용된 연결이 없으면 요청 모델에 기존 쿼터와 예산이 그대로 적용되며, 폴백이 차단을 우회하지 않습니다. 참조 구현의 `onExhausted: deny` 옵션은 배포된 유효 정책·APIM 경로에 구현되어 있지 않으며 콘솔에서도 제공하지 않습니다.

## 사용량

![사용량 화면](images/console-usage.png)

사용량은 이 게이트웨이가 계측한 토큰 단위로 보고합니다. 게이트웨이를 통과한 요청만 집계하며, 다른 경로로 모델에 도달한 요청은 포함하지 않습니다. 콘솔의 어떤 화면도 전체 사용량을 보여준다고 주장하지 않습니다.

배너에는 기간의 날짜뿐 아니라 기간 자체에 대한 정보가 표시됩니다. 시작·종료 시각, 읽은 시각, 수집 지연(데이터가 반영되기까지의 지연), 마감 여부를 보여줍니다. 아직 마감되지 않았거나 수집 지연 기간 안에 읽힌 기간은 최종 수치가 아니라 해당 상태를 나타내는 라벨과 함께 표시됩니다.

**사람은 이름이 아니라 가명화된 키로 표시됩니다.** 각 행은 집계값이며 프롬프트나 응답 본문은 이 화면에 반환되지 않습니다. 키와 사람의 매핑은 콘솔에서 제공하지 않습니다.

가명화는 익명화를 의미하지 않습니다. 조직에서 개인과 연결할 수 있다면 subject 또는 애플리케이션 키에 모델, 토큰, 정책 결과, 시간 정보가 결합된 정보도 여전히 개인 데이터일 수 있습니다.

개발자를 온보딩하기 전에는 모니터링 목적, 데이터 범주, 수신자, 접근 규칙, 보존·삭제 기간, 문제 에스컬레이션 또는 권리 행사 경로, 키 보관 및 재식별 규칙을 문서화하고 조직의 승인을 받아야 합니다. 이 콘솔이 메시지 본문을 반환하지 않더라도 제공자와 플랫폼 진단 정보는 별도로 검토해야 합니다. 이 PoC는 조직의 승인이나 모니터링 안내를 대신 제공하지 않습니다.

## 사용자와 그룹

![사용자와 그룹 화면](images/console-users-groups.png)

이 화면에서는 거버넌스 대상인 각 팀의 구성원과 최종 적용 정책을 확인하고, 사용 권한을 변경할 수 있습니다.

화면 위쪽의 디렉터리 조회 결과는 읽기 결과이며 읽기 전용입니다. 게시된 거버넌스 설정에서 팀으로 지정한 그룹만 조회하므로 디렉터리 브라우저가 아니며, 여기서 임의의 사람이나 그룹을 찾을 수 없습니다. 아래의 이용 권한 폼은 변경 한 건을 초안으로 저장하고 해당 리비전을 반환합니다. 저장만으로 활성 이용 권한이 바뀌지는 않습니다. [게시](#게시)의 승인 및 게시 절차를 거쳐 모든 대상이 확인한 뒤에 새 요청부터 적용됩니다.

디렉터리 읽기 작업에는 배포가 자동으로 부여하지 않는 Microsoft Graph 권한이 필요합니다. 관리자가 권한을 부여하기 전까지 조회는 `reading_unavailable / directory-snapshot-absent`로 거부됩니다. 권한이 있는 관리자의 이용 권한 및 역할 할당 작성은 이 조회와 독립적으로 제공되며, 디렉터리 선택기 대신 직접 입력한 키와 게시된 팀 매핑을 사용합니다. 권한을 부여할 수 있는 주체와 방법은 [Entra: Users와 Groups 화면을 위한 디렉터리 읽기 권한](01-deployment_ko.md#entra-users--groups-화면을-위한-디렉터리-읽기-권한)에서 설명합니다.

### 모델 이용 권한과 토큰 한도 편집

이용 권한 편집기에는 선택한 바인딩의 허용 모델, 분당 요청 수, 분당 토큰 수, 토큰 쿼터와 기간이 표시됩니다. 다른 바인딩을 선택하면 해당 바인딩의 값으로 다시 채워집니다. 이용 권한의 한도와 예산은 별개이며, 요청은 이 화면에서 편집한 값뿐 아니라 적용 가능한 모든 제어 조건을 충족해야 합니다.

1. 기존 이용 권한을 선택해 허용 모델과 한도를 편집하거나, 이용 권한 추가 폼에서 개인, 애플리케이션 또는 이미 등록한 거버넌스 팀을 대상으로 새 이용 권한을 만듭니다.
2. 개인과 애플리케이션에는 표시 이름이나 이메일 주소가 아니라 게이트웨이가 사용하는 subject 또는 application 키를 입력합니다. 팀은 게시된 팀 매핑에서 선택합니다. 조직 전체의 상한은 기존 바인딩을 편집하며, 두 번째 조직 이용 권한으로 추가하지 않습니다.
3. 요청·토큰 속도 한도를 설정하고, 필요한 경우 토큰 쿼터와 기간을 함께 지정합니다. 기간은 `Hourly`, `Daily`, `Weekly`, `Monthly`, `Yearly` 중에서 선택합니다. 이 값은 금액이 아니라 토큰 기준 한도입니다.
4. 새 이용 권한에서 빈 필드는 한도를 추가하지 않습니다. 기존 한도를 편집할 때는 새 값을 명시해야 하며, 필드를 비워도 저장된 한도는 제거되지 않습니다. 토큰 쿼터와 기간은 함께 입력해야 합니다. 변경 사항이 없는 제출은 거부됩니다.
5. 초안을 제출한 뒤 [게시](#게시) 절차를 완료합니다. 게시 전에 새로 고침하면 초안의 제안 값이 아니라 활성 바인딩의 값이 표시됩니다.

활성 상태의 비전역 이용 권한은 철회(`state: revoked`)할 수 있으며, 철회되었지만 만료되지 않은 이용 권한은 복구(`state: active`)할 수 있습니다. 조직 상한은 철회할 수 없습니다. 비활성 바인딩은 모델과 한도를 유지하며, 복구하기 전까지 해당 필드는 읽기 전용입니다. 상태 변경 시 원래 부여 사유는 보존되고 리비전 이력에 변경자와 변경 내용이 기록됩니다. 철회는 삭제가 아닙니다. 제거 검증은 철회된 바인딩도 확인하므로, 참조된 팀이나 모델을 제거하려면 일관된 전체 설정 교체가 필요합니다.

### 거버넌스 정책 역할 할당

거버넌스 역할 부여 폼은 버전이 관리되는 거버넌스 역할 할당 스냅샷을 편집합니다. 지원되는 조합에서 역할, 할당 대상의 종류와 키, 범위를 선택하고 할당 식별자와 정해진 형식의 사유 코드를 입력합니다. 팀 범위의 할당에는 게시된 팀을 지정합니다. 역할 부여와 철회는 초안을 생성하며 동일한 승인 및 게시 절차를 거칩니다.

배포 환경에서는 이 작업으로 **Microsoft Entra 앱 역할을 할당하거나 관리 콘솔·API 접근 권한을 부여하지 않습니다.** 배포된 관리 기능의 권한은 호출자의 검증된 액세스 토큰에 포함된 앱 역할에서 결정되므로, 해당 역할은 Microsoft Entra에서 관리합니다. 스냅샷의 역할 할당은 거버넌스 정책의 역할·범위 판단 근거이며, 별도의 이용 권한 없이 모델 접근을 허용하지 않습니다. 로컬 데모 페르소나는 시연용 권한 판단에 스냅샷의 역할 할당을 사용하지만, 이는 배포된 Entra 접근 권한의 검증 결과가 아닙니다.

### 디렉터리 그룹을 거버넌스 대상으로 추가하기

이 화면은 디렉터리를 탐색하지 않으므로 그룹을 직접 지정해야 합니다. 팀 폼에는 팀 이름과 그룹의 **object ID**를 입력합니다. 제출하면 새 팀 매핑을 초안으로 저장하며, 활성 매핑은 바뀌지 않습니다. 디렉터리 조회 결과나 호출자 정책에 반영하려면 [게시](#게시)의 승인 및 게시 절차를 거쳐야 합니다.

object ID는 [Microsoft Entra admin center](https://entra.microsoft.com)의 **Entra ID** > **Groups** > **All groups**에서 확인합니다. 그룹을 선택한 뒤 overview에서 **Object ID**를 복사합니다. 이 값은 GUID입니다.

멤버십 자체는 디렉터리에 그대로 남습니다. 팀을 추가하는 작업은 이 제품이 어떤 그룹을 거버넌스 대상으로 삼을지 정할 뿐입니다. 그룹 구성원은 Entra에서 변경하며, 콘솔은 멤버십을 직접 변경하지 않습니다.

## 알림

![알림 화면](images/console-notifications.png)

알림에는 각 기간에 발생한 일, 전달 여부, 확인 여부가 기록됩니다. 카운터는 raised, awaiting delivery, delivered, failed, acknowledged를 구분해 보여주므로, 발생했지만 한 번도 전달되지 않은 사안도 사라지지 않고 해당 상태로 표시됩니다.

전달 채널은 이 화면에서 설정합니다. **주소는 저장한 뒤 다시 화면에 표시되지 않습니다.** 이후에는 host만 표시됩니다. 어떤 채널인지 확인하기에는 충분하지만 webhook을 복구할 수는 없습니다. 주소는 별도로 보관해야 하며, 잃어버리면 이전 값을 읽을 수 없으므로 새로 설정해야 합니다.

알림을 읽을 수 있어도 알림을 확인하거나 채널을 변경할 권한이 생기지는 않습니다. 변경 작업에는 notification write capability가 필요하며, 요청 내용을 읽거나 actor를 기록하기 전에 권한이 없으면 거부됩니다.

관리자가 콘솔에서 알림을 확인하는 방식으로 운영한다면 별도 채널은 필요하지 않습니다. 외부 채널 전송이 필요한 경우, 지원되는 두 채널의 요구 사항과 전달 방식은 [채팅 채널로 거버넌스 알림 보내기](05-notifications_ko.md)에서 확인할 수 있습니다.

## 변경 이력

![변경 이력 화면](images/console-audit.png)

모든 거버넌스 변경 사항이 기록된 actor code, 버전, 사유, 변경 당시의 설정과 함께 표시됩니다. 화면에는 현재 보고 있는 scope에서 이 기록이 포함하는 범위를 설명하는 문장이 있어, 항목 수가 적은 목록과 필터링된 목록을 구분할 수 있습니다. 배포된 관리자 actor code는 활성 키 버전에서 안정적인 가명이므로 개인의 직접 identifier를 노출하지 않고 관리자 작업을 구분할 수 있습니다.

**이것은 무엇이 바뀌었는지에 대한 기록이지, 위변조를 탐지하는 ledger는 아닙니다.** 기록 자체가 변조되었는지를 스스로 탐지한다고 주장하지 않습니다. 그런 속성이 필요하면 별도의 시스템에서 제공해야 합니다.

내보내기는 사본을 반출할 수 있는 권한이 있는 역할에게만 제공됩니다. 기록을 읽을 수 있지만 내보낼 수 없는 역할에는 컨트롤 대신 그 사실이 안내됩니다.
